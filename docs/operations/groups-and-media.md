# Private groups and SeaweedFS media

Create or join a private group from the chat sidebar. Owners/admins can rename it
and issue single-use invitations that expire after seven days. Owners can manage
admins, transfer ownership and remove members; members can leave. The owner must
transfer ownership before leaving. Removing or demoting an issuer permanently
revokes their outstanding invitations.

Each join creates a membership episode. History starts at that join, and rejoining
does not reveal messages from an earlier episode or the interval outside the group.
Late requests from old tabs cannot send, acknowledge reads or bind uploads using
the old episode. Removal invalidations purge the corresponding browser cache,
drafts, uploads and pending sends. Group receipts show member names/counts, and
typing can show multiple members.

`GROUP_MAX_MEMBERS` defaults to 100 and accepts 2–1000, counting the owner and all
active members. Set it in the API and worker environment and restart them through
the deployment's process manager; changing the environment file alone does not
change an already running process.

The composer accepts images and generic files, including file-only messages.
Upload progress, cancel and retry share the authenticated session lifetime. A send
freezes the ordered ready attachment IDs alongside its client message ID; retries
must match that content. Settings uses the same upload flow for profile avatars.

## Storage configuration

| Variable                                   | Development default / purpose                                  |
| ------------------------------------------ | -------------------------------------------------------------- |
| `SEAWEED_ACCESS_KEY`, `SEAWEED_SECRET_KEY` | Private credentials generated by `node scripts/init-env.mjs`   |
| `MEDIA_S3_INTERNAL_ENDPOINT`               | `http://127.0.0.1:8333`; server-only S3 endpoint               |
| `MEDIA_S3_PUBLIC_ENDPOINT`                 | `http://localhost:8336`; exact endpoint used when signing      |
| `MEDIA_S3_BUCKET`                          | `chat-media`; private bucket initialized by `admin media-init` |
| `MEDIA_S3_REGION`                          | `us-east-1`                                                    |
| `MEDIA_USER_QUOTA_BYTES`                   | `1073741824` (1 GiB); staging, candidates and published bytes  |
| `CHAT_MEDIA_ORIGIN`                        | `http://localhost:8336`; frontend build and media proxy origin |

In production, set the internal endpoint to the private SeaweedFS S3 service and
the public endpoint to `CHAT_MEDIA_ORIGIN`. Configure both app/media DNS names,
rebuild static assets, and run `admin media-init` with the API's storage environment
after storage starts. Follow the platform-independent [deployment guide](deployment.md).
Missing media
credentials disable uploads; text authentication/messages do not depend on storage
initialization or availability. Credentials, actual policies and signed URLs must
stay out of Git and logs.

## Limits and guarantees

- A file is 1 byte–50 MiB. A message contains at most 10 files; a user has at most
  10 pending uploads. New attempts consume their own quota until safe cleanup.
- Upload grants last 10 minutes and download grants 60 seconds. Public ingress has
  a 600-second upload-body deadline and 30-second upstream response deadline;
  staging reservations remain for 660 seconds after grant expiry before deletion
  and quota release. Keep that grace aligned with ingress deadlines. SeaweedFS
  finalization uses background storage work, so a stalled internal operation can
  recreate a retired logical key after that window. The media worker retains the
  ledger tombstone and retries deletion hourly, including after dependency failures.
  Each pass handles at most 50 due retired keys, ordered by the oldest attempt;
  backlog and outages can delay reconciliation. The worker rechecks retirement and
  active references before each bounded storage delete, without releasing quota again.
  Keep these tombstone rows when maintaining the database: their identities are
  required to find late arrivals. Reconciliation guarantees eventual retry of
  tracked logical keys while the worker and storage recover; physical volume-chunk
  reclamation and a hard disk-usage bound remain outside the verified guarantee.
- Unfinished uploads expire after one hour; ready unbound uploads after 24 hours.
  Cleanup is retryable and releases quota only after tracked object deletion.
  Migration `0010_media_reconciliation.sql` adds durable retry scheduling for
  already retired keys; migration `0009_media.sql` remains unchanged.
- Inspect PNG/JPEG/WebP bytes rather than trusting declared MIME. Bound dimensions
  to 8192 per axis, 20 million pixels and two concurrent processors. Decoder
  allocation limits are best effort; their 128 MiB budget is not process isolation.
  Avatars/thumbnails are sanitized PNG. Generic files use octet-stream and attachment
  disposition. The media origin returns `nosniff` and private/no-store.
- Completion seals the staging ETag; workers use conditional copy into unique
  immutable candidates. Message/event/outbox/reference writes share a transaction.
  Lease expiry, cancellation and cleanup fence stale publication. Storage work runs
  in a separate durable loop so realtime fanout can continue through storage outages.
- Downloads recheck actor, conversation history bounds and the current avatar
  pointer. A previously issued grant remains a short-lived capability until expiry.
  Only visible previews renew grants; logout/removal tears down related requests.

This is a single-host small-team release. End-to-end encryption, public channels,
voice/video and multi-host storage remain future work. Message editing, withdrawal,
search and contextual history are covered by [chat experience](chat-experience.md).
PWA installation, updates and background push are implemented; see
[PWA and background notifications](pwa-notifications.md) for configuration and
the remaining deployment/device acceptance requirements.

## Verification

```powershell
node scripts/check.mjs --integration
```

The suite uses real PostgreSQL, Valkey, Centrifugo, SeaweedFS and browsers. Each
browser stack owns a unique test database/bucket. Follow the coordinated
[backup/restore procedure](backup-restore.md) before upgrading storage or migrations.
See [CI](continuous-integration.md) for disposable GitHub service wiring.
Validate an actual HTTPS staging deployment with the platform-independent checks
in [production deployment](deployment.md).
